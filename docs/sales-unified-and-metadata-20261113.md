# 销售订单统一列表与独立业务记录

## 已实现

商城订单与业务订单采用相同的列表组织方式：取消占空间的独立标题说明区，将筛选、导出和录入操作放进列表工具栏。商城原状态页签改为紧凑状态下拉，导出支持当前筛选结果以及所选订单；数量、分页和含税金额合计位于列表底部。金额保留原始小数精度，不使用浮点累加。

业务订单按商城列结构展示订单／日期、客户／收货人、商品明细、金额、配送／物流、状态及操作。客户需求、项目、付款、出货、商品与原操作流程继续保留；商品、快递单号来自该业务订单真实接口，不复制商城订单、收货信息或退款记录。

只有一个页面的入库管理改为一级直达菜单。其他多页菜单保留；下拉菜单采用内容宽度和实际面板测量，同层等宽、父子层分别测量定位，不再强制固定宽度。字体、手机抽屉、键盘导航、权限撤销及询价提醒保持。

## 独立收货信息与售后管理

具有当前商户业务订单写权限的账号，可以在业务订单行菜单中编辑收货人、电话、地址、备注，登记或更新售后记录。售后类型为咨询、维修、换货、退货申请和退款申请；登记、处理中、已结案仅代表记录状态，不能解释为已退款或已退库。

历史缺失收货信息明确显示未录入，不将客户联系人冒充收货人、不回填历史资料。记录存放在五张独立表中，原订单、客户、付款、库存、商城退款与实验单归档登记不作变更。

四个新增固定端点为 `crmSalesOrder.metadataGet`、`saveReceiver`、`addAfterSale`、`updateAfterSale`。每次请求使用原商户／员工／订单读写授权栅栏，交集客户读取权限，并先执行原 `crmSalesOrder.get` 验证真实订单可见范围。商户、订单号、客户与审计操作者均由服务器推导；输入严格校验，不接受客户端伪造归属或操作者。

事务使用单连接、版本 CAS、请求幂等键及追加审计。版本冲突不覆盖他人修改，重放仍须重新验证可见范围。界面同时要求当前商户精确 `crm.sales_orders` 可读／可写能力，未核验、只读、其他模块授权和其他商户均不可借权。

## 验证与发布

后端实际候选字节隔离测试 53 项通过，前端实际候选交互测试 31 项通过；定向源码回归和 TypeScript 检查通过。原金融操作处理器及所有对话框后续源码保全检查通过。测试全部使用虚构 fixture，未代用户保存真实收货、售后、收款、出货或退款记录。

独立表准备与真实 MySQL 默认日期解析已核验；原服务连接未被改变。发布顺序为新增 API 先行、前端资源随后切换。后端仅重载后台单进程，前端六文件增量发布；保留旧资源、代码及 HTML 精确回滚基线。原主站、无关进程、客户默认首页、登录回跳、询价和原实验单归档规则保持。

生产只读探针执行原归档服务的实际未变字节，核验实验单仍被排除，原订单、付款关联、库存、合同与买家详情记录未被本次修改。没有执行已登录浏览器的真实订单写入验收；原页面真实业务数据写入不是测试手段。

后续 schema 生成配置已包含主 schema、原归档表及新独立表，避免遗漏。不要在该生产库运行全库推送来代替本次限定迁移。运行时完整备份、发布包和实际订单范围只留私有运维目录；公开仓库仅保存通用源码、虚构测试及脱敏证据。
