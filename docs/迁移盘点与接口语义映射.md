## 二、技术结构与固定入口

合并后的代码已处于用户要求的 **React + Express + tRPC + Drizzle** 结构中。构建脚本、依赖版本与生产子路径构建入口位于 `package.json`；数据库定义固定在 `drizzle/schema.ts`；所有数据库访问函数由 `server/db.ts` 导出；所有 tRPC API 由 `server/routers.ts` 的 `appRouter` 统一导出；页面与业务组件分别位于 `client/src/pages/` 与 `client/src/components/`。[1] [2] [3] [4]

| 层级 | 固定入口 | 当前实现 |
|---|---|---|
| 数据库 Schema | `drizzle/schema.ts` | 18 张表、类型和枚举定义 |
| 数据访问层 | `server/db.ts` | 物料、商户、CRM、后台账号、消息、前台跨库物料 |
| API 路由层 | `server/routers.ts` | 9 个顶层路由模块，统一输入校验与权限控制 |
| 页面层 | `client/src/pages/` | 9 个页面文件，其中 5 个实际业务路由页面 |
| 组件层 | `client/src/components/` | 统一布局、登录辅助、管理后台共享组件与模板 UI |
| 后台布局 | `client/src/components/DashboardLayout.tsx` | 必选布局，带权限菜单、移动端页头和消息角标 |

## 三、业务模块盘点

当前源仓库 HEAD 的实际可用后台范围以物料、商户、消息和后台用户管理为主。仓库内较早的 `PROJECT_INFO.md` 仍描述商品、订单、退款、财务、风控和审计页面，但这些模块在当前 HEAD 中只保留数据库表结构，未注册对应的页面与 tRPC 路由，因此交付和验收应以当前代码事实为准，而不能把预留表误报为已启用功能。[2] [3] [5]

| 模块 | 前端路由 | tRPC 路由 | 数据访问 | 当前状态 |

| 后台登录与找回 | `/login` | `auth.*` | 后台账号、验证码函数 | 已实现 |
| 物料数据库 | `/` | `material.*` | 公开搜索、后台 CRUD、图片与 PDF 元数据 | 已实现 |
| 商户管理 | `/merchants` | `merchant.list/review/setCrmStatus/sendMessage` | 商户审核、CRM 与发信 | 已实现 |
| 商户详情 | `/merchants/:id` | `merchant.detail`、`platformMaterial.*` | 商户详情与前台跨库物料 | 已实现 |
| 消息中心 | `/messages` | `message.*` | 前后台会话、未读计数与回复 | 已实现 |
| 后台用户 | `/admins` | `admin.*`、`adminUser.*` | 账号 CRUD、状态与角色 | 已实现 |
| 前台对接 | 无后台页面 | `portal.*` | 入驻、CRM 申请、留言、图片回写 | 已实现，需 `PORTAL_API_KEY` |
| 商品、订单、退款、财务 | 未注册 | 未注册 | 仅 Schema 预留 | 未启用 |
| 告警、风控、审计 | 未注册 | 未注册 | 仅 Schema 预留 | 未启用 |

## 四、tRPC 接口语义映射

迁移没有重命名当前源仓库的 procedure。输入继续由 Zod 校验，公开前台接口继续通过 `x-portal-key` 与 `PORTAL_API_KEY` 比对；后台接口继续使用共享 RBAC 权限矩阵，服务端与前端使用同一份角色权限定义。[3] [10]

| 路由模块 | 保留的 procedure | 关键语义 |
|---|---|---|
| `auth` | `me`、`logout`、`login`、`changePassword`、`resetChannels`、`requestReset`、`resetPassword`、`requestUsernameRecovery`、`recoverUsername` | Manus OAuth 与本地后台账号共存；会话 Cookie 行为保持不变 |
| `material` | `lookup`、`getSpecs`、`search`、`list`、`detail`、`categories`、`brands`、`create`、`update`、`toggleStatus`、`remove`、`uploadDatasheet`、`uploadImage` | 前台公开搜索与后台 CRUD 分离；PDF/图片继续校验大小与文件魔数 |
| `merchant` | `list`、`detail`、`review`、`setCrmStatus`、`sendMessage` | 审核动作映射、CRM 状态和商户发信行为保持不变 |
| `portal` | `submitMerchant`、`submitMessage`、`submitCrmApplication`、`getMessages`、`getUnread`、`getCrmAccess`、`uploadMaterialImage` | `x-portal-key` 鉴权、按信用代码幂等、消息未读及本地图片回写保持不变 |
| `message` | `threads`、`detail`、`reply`、`setStatus`、`unreadCount` | 打开详情清零后台未读；拉取前台消息清零前台未读；回复重新打开会话 |
| `platformMaterial` | `list`、`offshelf` | 通过生产 RDS 跨库读取；下架写回 `draft` 并保存必填原因 |
| `admin` | `list` | 保留兼容列表入口 |
| `adminUser` | `list`、`create`、`update`、`toggleStatus`、`remove` | 仅 `admins.manage` 权限可用；密码仍以 bcrypt 哈希保存 |

## 五、数据库 Schema 与迁移盘点

`drizzle/schema.ts` 当前定义 18 张表，现有迁移目录包含 16 个 SQL 文件。核心启用表覆盖用户、后台账号、密码重置、物料、商户与前后台消息；其余表作为后续商品、订单、财务、告警、风控和审计模块的结构预留。[2]

| 领域 | 表名 | 使用状态 |
|---|---|---|
| 用户与权限 | `users`、`admin_users`、`password_reset_codes` | 已使用 |
| 物料主数据 | `materials` | 已使用 |
| 商户 | `merchants` | 已使用 |
| 消息 | `message_threads`、`messages` | 已使用 |
| 商品与库存 | `categories`、`products`、`inventory_logs` | Schema 预留 |
| 订单 | `orders`、`order_status_logs` | Schema 预留 |
| 售后与财务 | `refunds`、`payment_flows`、`settlement_bills` | Schema 预留 |
| 治理 | `audit_logs`、`alerts`、`risk_analyses` | Schema 预留 |

迁移文件中同时存在两个 `0000_*.sql`。这反映仓库早期迁移历史分叉，不能在未核对目标库现状与 `__drizzle_migrations` 记录的情况下直接把全部 SQL 依文件名重放到生产库。后续数据库阶段应先生成当前 Schema 与目标数据库的差异，再执行经审查的幂等迁移，避免重复建表。

## 六、前端路由与 DashboardLayout

`client/src/App.tsx` 将 `/login` 设为公开路由，其余业务路由全部经过 `AuthGate`。物料、商户、消息和后台用户页面分别由 `PermissionGate` 执行模块权限判断；登录成功后通过经过归一化的 `next` 参数返回原页面。[5]

所有管理后台业务页面均直接或通过权限门卫渲染现有 `DashboardLayout`。该布局保留模板侧边栏框架，按角色过滤菜单，通过 `trpc.message.unreadCount` 每 30 秒轮询消息角标，并支持可折叠、可调整宽度的桌面侧边栏与移动端固定页头。[6]

| 页面 | 路径 | 权限 | 布局 |
|---|---|---|---|
| `Login.tsx` | `/login` | 公开 | 独立登录页 |
| `Materials.tsx` | `/` | `materials.read` | `DashboardLayout` |
| `Merchants.tsx` | `/merchants` | `merchants.read` | `DashboardLayout` |
| `MerchantDetail.tsx` | `/merchants/:id` | `merchants.read` | `DashboardLayout` |
| `Messages.tsx` | `/messages` | `messages.read` | `DashboardLayout` |
| `Admins.tsx` | `/admins` | `admins.manage` | `DashboardLayout` |

## 八、ECS 运行前置条件

现有生产形态使用 PM2 启动 `dist/index.js`，Nginx 将 `/admin/` 去除前缀后代理到应用端口，并单独映射 `/admin/uploads/`。仓库内已经提供 PM2 与 Nginx 示例，但原文档仍写有旧服务器 IP `47.97.108.147`；本次交付必须统一改为新目标 `8.154.34.152`。[7] [8] [9]

| 环境变量 | 作用 | ECS 要求 |
|---|---|---|
| `DATABASE_URL` | 后台 MySQL/RDS 连接 | 必填，不入库 |
| `JWT_SECRET` | 会话签名 | 必填，不入库 |
| `PORTAL_API_KEY` | 前台对接请求头鉴权 | 启用前台对接时必填 |
| `UPLOAD_DIR` | 本地图片持久目录 | 建议 `/opt/apps/dianzi51-admin/uploads` |
| `PLATFORM_DB_NAME` | 前台跨库数据库名 | 默认 `dianzi51` |
| `SMS_*` | 短信找回密码 | 启用真实短信时配置 |
| `VITE_BASE_PATH` | 前端构建 base | `/admin/` |
| `PORT` | Express 监听端口 | PM2 示例为 `3001` |

## 九、下一阶段实施边界

代码迁移本身已经完成，后续重点不是重新改写现有业务，而是验证 Schema 与当前 WebDev 数据库的一致性、补齐目标 IP 的 ECS 自动化配置、修正开发预览地址输出、运行完整测试与构建门禁，并对关键页面进行桌面和移动端复查。对真实 RDS 的迁移和对 `8.154.34.152` 的 SSH 操作均属于外部生产变更，必须在取得服务器登录方式、数据库凭据和明确执行授权后再进行。
