# `/admin/` 登录成功后闪退诊断记录

**报告日期：** 2026-08-03  
**问题来源：** 用户截图与线上只读访问  
**生产入口：** `http://51dianzi.com/admin/login?next=%2F`

## 已确认现象

用户报告在后台登录成功后页面立即退出或重新回到登录页。截图显示浏览器通过 HTTP 访问 `51dianzi.com/admin/login?next=%2F`，页面位于 `/admin/` 子路径，浏览器明确标记连接为“不安全”。

## 线上只读探测

未输入账号、未提交登录表单的只读探测结果如下：

| 请求 | HTTP 状态 | 返回值 |
|---|---:|---|
| `GET /admin/api/trpc/auth.me` | 200 | `{"result":{"data":{"json":null}}}` |
| `GET /api/trpc/auth.me` | 200 | `{"result":{"data":{"json":null}}}` |

这说明 Nginx 当前同时把 `/admin/api/trpc` 与 `/api/trpc` 路由到了后台服务，未登录状态下两条路径均可正常返回 JSON。页面的 `document.baseURI` 为 `http://51dianzi.com/admin/login?next=%2F`，当前浏览器没有可读 Cookie（会话 Cookie 应为 HttpOnly，因此此项本身不能证明服务端是否设置成功）。

## Cookie 与代理排除结果

服务端 `getSessionCookieOptions()` 会按 `req.protocol` 或 `X-Forwarded-Proto` 判断是否安全连接：HTTPS 使用 `SameSite=None; Secure`，HTTP 使用 `SameSite=Lax` 且不加 `Secure`，Cookie 路径为 `/`。已对公开的 `auth.logout` mutation 做无会话调用并检查响应头，生产返回：

```text
Set-Cookie: app_session_id=; Max-Age=-1; Path=/; HttpOnly; SameSite=Lax
```

因此，生产 HTTP 请求当前被服务端正确识别为非安全连接，**可排除 Nginx 错传 `X-Forwarded-Proto: https` 导致 `Secure` Cookie 不回传的假设**。

前端 `next=%2F` 经 `normalizeAdminReturnPath` 归一化为后台根路径，`WouterRouter` 的 base 为构建时 `/admin`；现有 `client/src/lib/adminRoutes.test.ts` 同时覆盖了目标路径恢复、外部地址拒绝和 `/login` 循环拒绝。`pnpm build:admin` 与 `pnpm verify:admin-build` 均通过。因此，`next` 与子路径构建也不是当前闪退根因。

## 已确认根因

本地管理员登录在 `server/adminAuth.ts` 中调用 `sdk.createSessionToken`。该方法在 `server/_core/sdk.ts` 中把 `ENV.appId` 写入 JWT，而 `ENV.appId` 来自 `VITE_APP_ID`。紧随登录后的 `auth.me` 请求会调用 `sdk.verifySession`；该校验要求 `openId`、`appId`、`name` 三项都是非空字符串。

仓库内生产 PM2 模板只声明 `JWT_SECRET`、数据库、门户和短信等环境变量，`deploy/`、`docs/` 与 `scripts/` 对 `VITE_APP_ID` 的引用为零。因此，本地账号登录错误依赖了仅属于 Manus OAuth 的可选应用 ID。

使用原始签发与校验代码进行一次性对照实验，结果如下；诊断脚本运行后已删除，未进入仓库：

| 条件 | `createSessionToken` | `verifySession` | 结果 |
|---|---|---|---|
| `VITE_APP_ID=''` | 正常返回 Token | `Session payload missing required fields` | `tokenVerified=false` |
| `VITE_APP_ID='51dianzi-admin-diagnostic'` | 正常返回 Token | 成功恢复 `local_admin:1` | `tokenVerified=true` |

这解释了完整现象：密码校验与 Cookie 写入先成功，前端随后刷新 `auth.me`；新请求因 JWT 中 `appId` 为空而无法恢复用户，`LoginRoute` 继续渲染登录页，用户看到“登录成功后闪退”。`utils.invalidate()` 只是触发了必要的服务端会话复核，并非根因。

## 最小修复边界

修复应仅让本地管理员 JWT 使用明确、非敏感、非空的本地会话命名空间，继续沿用现有 `JWT_SECRET`、Cookie、账号状态、角色权限和过期时间。不得降低 `verifySession` 的字段校验，不得修改 OAuth、业务路由、数据库 Schema、业务 SQL 或前端门卫。完整影响面与回归矩阵见 `docs/登录闪退修复前项目逻辑审查报告.md`。

## 修复后预览记录

重启开发服务后，服务正常监听 3000 端口，重启后的日志未出现新的模块加载、TypeScript 或启动错误。使用不带会话的隔离浏览器访问 `/login?next=%2F`，页面稳定渲染后台账号密码登录表单，用户名、密码、显示密码、登录、忘记用户名和忘记密码入口均可达；未发生路由循环或自动跳离登录页。

WebDev 管理预览自带托管环境自动登录会话，因此其 390px 截图进入物料页而非本地登录页。该截图只证明现有 DashboardLayout 和物料页在移动视口继续可用，不能替代本地账号的生产登录验证。本次没有创建测试管理员、没有向隔离库或生产库写入账号数据，也没有使用生产凭据。
