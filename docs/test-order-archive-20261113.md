# 后台实验商城订单逻辑归档

2026-11-13已完成并上线。用户明确确认的固定10笔实验订单，仅在后台商城正常视图中逻辑归档，不物理删除原记录。具体商户、卖方、订单清单、完整私有备份、元数据维护工具和完整运行回执不提交此公开仓库；运维方私有保管。本文只说明通用实现。

## 通用过滤与权限

新增服务位于 `server/services/businessTestOrderArchive.ts`。后台 `forwardBusinessMethod` 仅对固定 `order.sellerOrders` 方法，在原实时员工绑定、商户和企业范围授权栅栏内、原前台卖方命令成功后，对返回数组做精确过滤。不会将后台原生角色或任意浏览器参数拼接为订单授权。

独立后台登记中的 merchantId、sellerUserId、orderId、orderNo、originalStatus、isTest 和 state 均须匹配。只有用户已确认的 archived / isTest=1 / 原cancel订单可被排除；ID与订单号必须成对匹配。已恢复登记、非cancel新状态、其他商户／卖方和不匹配行保持原对象、顺序和全部属性，不修改原数组。

正常列表、状态数量、金额统计和导出继续使用同一后台 sellerOrders 数组，没有合并CRM业务订单金额。前台买家列表、原详情、合同、收款、退款、发货和库存流程不变。没有新增公开归档、恢复接口或动态method selector。

登记服务只使用参数化 admin DB SELECT，读取七个最小匹配字段，不返回私有备份或操作确认信息。缺表、DB不可用、错误形状或非法metadata均返回服务暂不可用，不把未过滤数组冒充正常成功，也不继续原成功命令审计。其他业务方法不读取归档登记。

## 独立表与可恢复性

`drizzle/businessTestOrderArchiveSchema.ts` 定义独立登记表和追加式审计表，不改原主schema或订单表。预先独立建表；请求服务不创建表、不写审计、不更新业务表。维护工具只写登记、追加审计，恢复按准确范围／批次／revision条件更新登记state并追加restore审计，原订单、资金、库存、合同不动。

本批次操作来源是用户任务中的明确确认，不冒充被核查的后台账号登录操作。审计区分 user_task_confirmation、admin_session 和 maintenance_cli；没有真实后台会话时对应adminId为空。

私有完整备份、原订单行指纹和完整备份回执哈希独立保存。代码回滚与登记恢复分开；撤回过滤会使测试订单重新在正常视图可见，不能把代码回滚后仍有metadata当作归档排除已生效。

新增服务、真实router mock集成和独立schema测试使用虚构商户／卖方／订单fixtures；定向4文件114项全部通过，类型检查通过。实际生产候选22项隔离检查、独立只读审查及真实数据只读核验通过，准确范围与完整回执私有保管。

最终当前绑定范围正常列表3笔、已发货3笔、已取消0笔；原13笔订单及关联记录哈希未变。恢复显示内存模拟可使13笔重新可见，未在生产实际恢复。没有代用户确认收款、取消、退款或发货，也不把首页200当成真实登录浏览器验收。

后台API只增加两处精确插入，原关键授权和平台命令不变。仅后台API进程必要重载，主站API、已上线前端整合和其他进程未变。代码通过检查后同步原公开仓库，敏感运维材料不公开上传。
