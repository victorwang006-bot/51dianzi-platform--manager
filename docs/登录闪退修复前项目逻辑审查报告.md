# 登录闪退修复前项目逻辑审查报告

**审查日期：2026-08-03**  
**审查范围：前端路由与页面、tRPC 客户端、Express/tRPC 服务端、JWT 与 Cookie、管理员账号体系、数据库访问层、Drizzle Schema、权限模型、上传与短信、Vite 构建、Nginx 与 PM2 生产契约、现有自动化测试。**

> 本报告形成前未修改任何登录、权限、业务接口、数据库 Schema 或部署代码。审查的目的，是先建立完整调用图、行为不变量和修复前基线，再限定最小修改范围，避免登录修复引入跨模块回归。

## 一、结论摘要

项目是一个部署在 `/admin/` 子路径下的 React 19 + Wouter + tRPC 11 + Express + Drizzle 管理后台。后台采用本地 `admin_users` 账号密码登录，同时保留 Manus OAuth 兼容链路。登录成功后的所有后台能力，都依赖同一个 `app_session_id` JWT 被 `createContext` 恢复为 `ctx.user` 与 `ctx.adminAccount`；一旦该恢复失败，`AuthGate` 会回到登录页，所有受保护 procedure 也会被统一拒绝。

本次审查确认了一个可重复、确定性的根因：**本地管理员登录调用 `sdk.createSessionToken`，该函数把 `ENV.appId`（即 `VITE_APP_ID`）写入 JWT；但生产 PM2 模板和全部生产部署文档均未声明 `VITE_APP_ID`。当该变量为空时，登录接口仍会成功校验密码、写入 Cookie，但紧接着的 `auth.me` 请求会在 `verifySession` 中因为 `appId` 为空而判定 Token 无效，前端因此再次显示登录页。** 这与用户观察到的“登录成功后闪退”完全一致。

| 修复前审查项 | 结果 | 结论 |
|---|---:|---|
| TypeScript `pnpm check` | 通过 | 当前源码类型基线正常 |
| `/admin/` 生产构建 `pnpm build:admin` | 通过 | 静态资源能够按子路径构建 |
| `/admin/` 构建自检 | 通过 | 资源路径、Router base 与 tRPC base 未残留根路径配置 |
| Vitest | 5 个文件通过，10 个文件失败 | 共 75 项：29 通过、11 失败、35 跳过；11 项失败均由隔离开发库缺少业务表导致，不是本次代码回归 |
| Cookie 协议属性 | 已排除 | 生产 HTTP 实测为 `SameSite=Lax` 且不带 `Secure`，不是 Secure Cookie 被浏览器丢弃 |
| Nginx `/admin/` 代理 | 契约一致 | 带尾斜杠 `proxy_pass` 去除 `/admin/` 前缀，转发 Host 与协议头，和客户端 `/admin/api/trpc` 契约一致 |
| JWT 对照实验 | 根因复现 | `VITE_APP_ID=''` 时签发后立即校验失败；设置非空值后同一链路校验成功 |

## 二、整体架构与调用关系

管理后台前端由 `client/src/main.tsx` 创建共享 QueryClient 与 tRPC 客户端，API 固定请求 `${BASE_URL}/api/trpc` 并携带 Cookie。`client/src/App.tsx` 使用 Wouter 的 `base` 适配 `/admin/`，由 `LoginRoute`、`AuthGate` 和 `PermissionGate` 依次处理登录态、受保护路由与角色权限。业务页面统一进入现有 `DashboardLayout`，没有另建第二套后台布局。

服务端由 Express 承载 tRPC。每次请求先在 `server/_core/context.ts` 中提取 Cookie 或 Bearer Token，经 `sdk.verifySession` 校验后，把 `local_admin:{id}` 映射到 `admin_users` 记录。`server/_core/trpc.ts` 的 `protectedProcedure` 与管理员权限中间件完全依赖该上下文。业务 procedure 集中在 `server/routers.ts`，数据库读写集中在 `server/db.ts`。

| 层级 | 关键文件 | 核心职责 | 登录修复必须保持的不变量 |
|---|---|---|---|
| 前端启动 | `client/src/main.tsx` | QueryClient、tRPC、`credentials: include`、`/admin/api/trpc` | 不改变 API base 与 Cookie 携带方式 |
| 路由与门卫 | `client/src/App.tsx` | Router base、登录页、AuthGate、PermissionGate | 未登录才进入 `/login`；登录后恢复原 `next`，拒绝外部跳转 |
| 认证 Hook | `client/src/_core/hooks/useAuth.ts` | 唯一 `auth.me` 查询、登出与缓存状态 | `auth.me` 是登录态唯一事实源；不得用本地伪状态绕过服务端 |
| 登录页 | `client/src/pages/Login.tsx` | 提交账号密码、显示错误、成功后刷新查询 | 不改变用户名/密码错误语义；成功后必须以服务端会话为准 |
| tRPC 上下文 | `server/_core/context.ts` | 提取 Token、验证 JWT、查询本地管理员 | 本地账号仅在存在且状态为 `active` 时恢复为管理员 |
| JWT | `server/_core/sdk.ts` | HS256 签发与验证 | `openId`、`appId`、`name` 均须为非空字符串；JWT_SECRET 必须一致 |
| 本地认证 | `server/adminAuth.ts` | bcrypt 校验、状态校验、签发 Cookie、记录登录时间 | 错误信息不得暴露账号存在性；停用/锁定账号不得登录 |
| 权限 | `server/_core/trpc.ts`、`shared/adminPermissions.ts` | 登录与角色权限拦截 | 修复不得放宽任何 procedure 权限 |
| 业务路由 | `server/routers.ts` | 认证、物料、商户、门户、消息、平台物料、管理员 | procedure 名称、输入输出、错误与副作用保持不变 |
| 数据访问 | `server/db.ts` | 全部业务查询、写入与跨库操作 | 不借登录修复改 Schema、SQL、事务或跨库权限 |

## 三、业务模块全景

现有后台的主业务链路已经按页面、procedure、数据库函数和权限逐项审查。登录修复的影响应被限制在会话签发与会话回归测试，不应触碰以下业务实现。

| 模块 | 前端入口 | tRPC 命名空间 | 主要数据与外部依赖 | 权限边界 |
|---|---|---|---|---|
| 物料数据库 | `/`、`Materials` | `material` | `materials`、本地上传/S3 | `materials.read` / `materials.write` |
| 商户管理 | `/merchants`、`/merchants/:id` | `merchant` | `merchants`、前台物料跨库查询 | `merchants.read` / `merchants.write` |
| 消息中心 | `/messages` | `message` | `message_threads`、`messages` | `messages.read` / `messages.write` |
| 后台用户 | `/admins` | `adminUser` | `admin_users`、bcrypt、密码重置码 | `admins.manage`，仅超级管理员 |
| 前台门户对接 | 无后台路由 | `portal` | 商户提交、CRM、留言、上传 | `x-portal-key`，不使用后台 Cookie |
| 前台平台物料 | 商户详情内嵌面板 | `platformMaterial` | `PLATFORM_DB_NAME` 跨库只读/下架 | 登录管理员与模块权限 |
| 系统与兼容认证 | 全局 | `system`、`auth` | JWT、Cookie、可选 Manus OAuth | 公开查询与受保护操作分离 |

Drizzle Schema 共定义 18 张业务表，覆盖 `users`、`materials`、`admin_users`、`password_reset_codes`、`merchants`、分类与商品、库存与订单、退款与支付结算、审计告警与风控、消息会话与消息。当前隔离开发库只有模板基础结构，现有数据库集成测试因此不能作为登录代码失败依据；本次修复不得以改业务逻辑或吞掉数据库错误的方式“修复”环境缺表。

## 四、登录成功后的精确时序

用户在 `/admin/login?next=%2F` 提交后，`auth.login` 调用 `loginWithPassword`。服务端查询 `admin_users`、执行 bcrypt 校验、检查账号状态、构造 `local_admin:{id}`，然后签发 JWT 并通过 `app_session_id` Cookie 返回。前端成功回调执行 `utils.invalidate()`，其中 `auth.me` 会立即重新请求。`createContext` 读取刚写入的 Cookie，调用 `verifySession`；只有 JWT 中 `openId`、`appId`、`name` 都非空，才继续查询管理员并返回用户。

| 时序 | 当前行为 | 空 `VITE_APP_ID` 时的结果 |
|---:|---|---|
| 1 | `auth.login` 校验账号密码 | 成功 |
| 2 | `sdk.createSessionToken` 使用 `ENV.appId` | 将空字符串写入 `appId` |
| 3 | 服务端设置 `app_session_id` | Cookie 被浏览器接收 |
| 4 | 登录成功回调刷新 `auth.me` | 发起新的认证请求 |
| 5 | `sdk.verifySession` 校验载荷 | 因 `appId` 不是非空字符串返回 `null` |
| 6 | `createContext` 无法恢复管理员 | `ctx.user = null` |
| 7 | `LoginRoute` 仍判定未登录 | 再次显示登录页，产生“闪退”感知 |
| 8 | 所有受保护 procedure | 后续均返回未登录或无权限 |

## 五、根因证据与已排除项

生产示例 `deploy/ecosystem.config.example.cjs` 以两个 PM2 cluster 实例运行，只传入 `NODE_ENV`、`PORT`、`UPLOAD_DIR`、`PLATFORM_DB_NAME`、`DATABASE_URL`、`JWT_SECRET`、门户密钥和短信变量。仓库内 `deploy/`、`docs/`、`scripts/` 对 `VITE_APP_ID` 的引用数为零。因此，生产部署契约与本地管理员 JWT 的隐式依赖不一致。

一次性诊断使用相同 `sdk.createSessionToken → sdk.verifySession` 链路。空 `VITE_APP_ID` 时日志为 `Session payload missing required fields` 且 `tokenVerified=false`；非空对照组为 `tokenVerified=true`，并正确恢复 `local_admin:1`。诊断脚本已在运行后删除，未进入仓库。

| 候选原因 | 审查结论 | 说明 |
|---|---|---|
| Cookie 被 `Secure` 属性丢弃 | 已排除 | 生产 HTTP 响应实测不带 `Secure`，使用 `SameSite=Lax` |
| `/admin/api/trpc` 路径错误 | 已排除 | 登录接口能够命中；构建自检确认 API base 与 Router base 均为 `/admin/` |
| `next=%2F` 开放跳转或登录循环 | 已排除 | `adminRoutes` 归一化逻辑拒绝外部地址和 `/login` 循环，已有纯单测 |
| Nginx 未去除 `/admin/` 前缀 | 已排除 | 配置采用带尾斜杠 `proxy_pass`，与应用根 `/api/trpc` 匹配 |
| 前端 `utils.invalidate()` 竞态 | 不是根因 | 会放大视觉切换，但只要 `auth.me` 返回有效用户，LoginRoute 会稳定进入目标页 |
| JWT 载荷 `appId` 为空 | 已确认 | 代码、生产配置缺口和本地对照实验三方一致 |
| PM2 两实例 JWT_SECRET 不一致 | 暂无证据 | 配置引用同一进程环境；仍应在上线前只读核验两个实例环境摘要，禁止输出密钥 |

## 六、允许修改的最小边界

最安全的修复原则是让**本地管理员会话不再依赖可选的 Manus OAuth `VITE_APP_ID`**，同时不放宽 `verifySession` 对 OAuth 会话载荷的校验。推荐由 `server/adminAuth.ts` 为本地管理员会话使用固定、非敏感、非空的会话命名空间（例如 `51dianzi-admin`），继续沿用现有 `JWT_SECRET`、`openId`、名称和过期时间。这样不会改变现有账号、密码、Cookie 名、权限、数据库、OAuth 回调或业务 procedure。

| 文件 | 允许的最小变更 | 明确禁止的变更 |
|---|---|---|
| `server/adminAuth.ts` | 本地管理员 JWT 使用明确非空的本地应用标识；保留现有 Cookie 与错误语义 | 不改账号查询、bcrypt、状态判断、Cookie 名、有效期或登录时间副作用 |
| 新增纯 Vitest 文件 | 覆盖不依赖 `VITE_APP_ID` 的签发与立即校验；覆盖 `local_admin:{id}` | 不连接生产库，不创建虚假业务数据 |
| `server/_core/sdk.ts` | 原则上不改 | 不降低 `verifySession` 的非空字段校验，不改变 OAuth 与 Cron 会话 |
| 前端文件 | 原则上不改 | 不以本地 `isLoggedIn` 状态绕过 `auth.me`，不取消 AuthGate 或权限门卫 |
| Schema、迁移、`server/db.ts`、业务页面 | 不改 | 登录修复不得夹带业务或数据库重构 |

## 七、修复后回归矩阵

修复后应先运行不依赖数据库的定向认证测试，再运行 TypeScript、完整 Vitest、`/admin/` 生产构建与构建自检。完整 Vitest 中因缺表造成的已知失败必须与修复前基线一致，不能新增非数据库类失败。获得有效测试账号后，还应在桌面与移动端验证登录、页面刷新、跨页面导航、退出、直接访问受保护路由和 `next` 回跳。

| 回归场景 | 预期结果 |
|---|---|
| 空 `VITE_APP_ID` 下签发本地管理员会话 | Token 能被立即验证，`appId` 为固定本地命名空间 |
| 正确账号密码登录 | Cookie 写入后 `auth.me` 返回管理员，进入原 `next` 页面 |
| 页面刷新与跨模块导航 | 登录态持续，角色权限不变化 |
| 错误密码、停用或锁定账号 | 保持原错误信息与拒绝行为 |
| 登出 | 清除同名 Cookie，返回 `/login` |
| Manus OAuth 会话 | 继续使用原 `ENV.appId` 与原回调逻辑，不被本地修复影响 |
| `/admin/` 构建自检 | 资源与 API 路径继续通过 |
| 业务测试 | 不新增失败；缺表导致的 11 项基线失败单独记录 |

## 八、审查结论

项目的业务模块、权限模型、前后端接口和生产子路径契约彼此关联清晰。当前登录闪退不是物料、商户、消息、管理员管理、数据库 Schema、DashboardLayout 或 Nginx 路径引起，而是**本地账号会话错误复用了 OAuth 应用 ID 的隐式前置条件**。修复可限制在本地会话签发和纯回归测试，不需要修改前端、数据库或任何业务接口，连锁风险可控。

## 九、实施与修复后验证
